# Briller Field Notes

Bilingual blog at `/en/blog/` and `/uk/blog/`. It is intentionally absent from header and footer menus. The standard website design, GitHub `preview` branch, local review and explicit deployment workflow apply.

## Add an article

1. Add `content/blog/posts/<slug>.md` and its Ukrainian translation at `content/blog/posts/uk/<slug>.md`. Keep the supplied article as editable Markdown, with a single H1 and optional italic byline. Raw HTML is disabled.
2. Add matching post entries in `content/blog/catalog.json` and `content/blog/catalog.uk.json`: unique slug, title, excerpt, editorial date, author, categories, tags, search keywords and an existing/local image with accurate alt text and caption.
3. Reuse category/tag IDs from the central catalog, or add meaningful new ones. A post may belong to several categories and tags. Only populated taxonomies get exported archive routes and sitemap entries.
4. Set `download` only when that article actually has an implemented resource/form. Put `{{download:builder-checklist}}` on its own line where the PDF preview and form should appear within the article; omit repeated checklist questions from the prose. The first resource is the supplied builder checklist. Add further resources to the form and server allowlist together; do not reuse the builder-checklist identifier for another file.
5. Build with `BRILLER_PREVIEW=1 npm run build`, check with `npm run check`, and run `BRILLER_PREVIEW=1 npm test`. Commit and publish `preview`. Deploy only on an explicit request.

The reusable layout provides article metadata, byline, cover caption, anchored table of contents, tables, blockquotes, source citations, topic links and a resource request area. Major-section numbering is decorative and removed during rendering; numbered checks and source lists stay intact. Current `[1]`–`[5]` references point to the corresponding ordered Sources list. Use this same numeric-source pattern when adding sourced posts, or extend the renderer deliberately for a different citation scheme.

The English Markdown file and PDF were imported from the user's attachments. The article's Sources section was subsequently reduced to the five relevant external technical references at the user's request; the English PDF remains unchanged. The Ukrainian companion PDF and preview are generated by `python3 scripts/build-uk-checklist.py` (ReportLab, PyMuPDF, Pillow, and the existing Node/sharp dependency). Both use local fonts; no remote assets are fetched. File instructions are article content; they are not operational instructions for the editor or application.

## Language and SEO

Both catalogs share post, category and tag slugs, while titles, descriptions, keywords and article text are localized. Interface copy is in `content/blog/interface.json`. Each locale searches its own article text. Footer EN/UK controls and the existing country/preference routing work for articles and archives, preserving query strings and fragments.

The old `/blog` and `/blog/...` routes permanently redirect to `/en/blog/...` in nginx, preserving query strings. `scripts/seo.mjs` also creates small static HTML fallback pages for local export previews, preserving query and fragment with JavaScript; production uses actual HTTP 301 responses. Only the localized canonical URLs are in the sitemap and llms.txt. Canonical, hreflang, x-default, Open Graph, HTML language and structured-data language are localized together.

For translated headings use a stable `{#english-heading-id}` suffix matching the English section ID. It is removed from visible text. This keeps table-of-contents anchors and footer language switching useful at the same section. Ukrainian-only headings without an explicit ID use Unicode-aware generated anchors. Keep numeric citations connected to `Sources` / `Джерела` lists.

Static HTML includes `Blog`/`BlogPosting` and breadcrumb structured data, title/description, canonical URL and social metadata. The first article in both languages uses its relevant room image for its social card; a dedicated branded OG image can be added later without changing the article. Preview builds remain noindex, including blog pages. Production builds include populated blog routes in the sitemap and llms.txt, without adding menu links.

## Search now

The browser searches article titles, excerpts, topic tags, explicit keywords and full article text. Results rank title matches first, then taxonomy/keywords, excerpts and body matches. All query words must match; category and tag filters narrow the same result set. Query/filter state can be shared in the URL. No query is sent to a model or tracking service.

## Suggested semantic-search extension

When enough posts exist to justify it:

1. Generate embeddings for published article chunks at build time; retain stable post slug, heading ID, title, categories and tags with each vector.
2. Add a server-side `/search` route to the small Cloud Run service. Keep the model API key in Secret Manager. Generate one query embedding, rank the stored vectors with cosine similarity and apply the selected category/tag filters. A build-generated vector file is sufficient for a modest library; add a vector database only when volume or update frequency calls for it.
3. Return article/heading links and excerpts. Preserve ordinary keyword search as the fallback if the provider times out or is unavailable. Do not promise generated technical advice from a search box.
4. Add query length/rate limits and explicit query-processing disclosure before enabling the service. Keep contact data separate from search queries.

No embeddings, paid model calls or claims of active AI search are included in the initial keyword-search implementation.

See [the Brevo setup guide](../../services/blog-leads/README.md). Real delivery requires the owner's service configuration. The form never reports success before the endpoint confirms storage. The supplied PDF is a public free download, not a secured paid asset.

## Localized resource delivery

The English PDF remains `/downloads/briller-builder-checklist-letter.pdf`. The Ukrainian A4 companion is `/downloads/briller-builder-checklist-uk.pdf`, with its own preview. The form submits `locale: en|uk`; the delivery service selects the matching email, privacy link and PDF. Older clients omitting locale retain English behavior. Unknown locales are rejected. No real emails are sent by unit/browser tests.

When releasing this change, deploy the updated resource service and the static website as a coordinated release. An old service only returns the English PDF; the new Ukrainian form deliberately rejects that mismatched result instead of claiming success. Resource-service changes are not activated by publishing the preview branch.

## Local development routing

`npm run dev` uses normal Next routing (without `output: export`) and permanent redirects from `/blog/...` to `/en/blog/...`. Production builds still use static export; nginx owns production redirects. This prevents export-only parameter errors for unknown local URLs after route changes. Restart the dev server after pulling configuration changes; if its previous build cache contains old routes, remove only the generated `.next` directory before starting again.

With the local server running, use `npm run test:dev -- http://127.0.0.1:3001` in a second terminal to check actual EN/UK blog routes, legacy redirects and unknown-page 404 behavior. These checks send no emails.
